# 签到系统优化方案：设备标识隔离 + 冷却状态机 + 防重入

> 参考实现：`smart-open/TraeWorkAssistant`（同为 Tauri 2 + React + Rust，MIT）
> 决策来源：用户已拍板三项（设备隔离用独立字段、纳入 aha 层、重试仅自动/静默生效）

## 一、Context（为什么做）

当前签到系统只有「日期」一维去重，缺三样东西：

1. **设备标识与机器码耦合**：`checkin.rs:305` 的 `X-Device-Id` 直接复用 `account.machine_id`，而 `machine_id` 同时还是 Trae `machineid` 文件值与注册表 `MachineGuid`。三者绑死意味着「换个签到设备号」必然连带改写 IDE 机器身份，无法单独旋转。
2. **无冷却**：`9074` 只弹一次 toast，可被立刻重试；连点「全部签到」或 GUI + `--silent` 双进程会重复打服务端。
3. **无防重入**：三个入口（`checkin_account` / `checkin_all_accounts` / `auto_checkin`）可并发，`account_manager` 锁只保护「读列表 / 写日期」两个瞬间，不覆盖网络段。

另有一个已确认的隔离缺口：切换账号的 12 步流程（`machine.rs:612`）**完全没处理** `%APPDATA%\Trae CN\aha\TinyStorage`（内含 `aha.device.device_id`）。

预期结果：设备号可独立旋转（用于从 9095「本设备今日已签到」自救）、限流有界退避、并发入口互斥、IDE 侧设备标识补齐 aha 层。

## 二、先厘清的两个事实（避免写进注释变成假结论）

### 1. 「X-Device-Id 必须是 16 位数字」**未经证实**

我此前的实测（同一 token 只换设备号）：
- `1234567890123456` → 稳定返回 `9095 当前设备今日已经签到`
- `8765432109876543`、随机 UUID、hex32、真实 `telemetry.machineId` → 均 `9074`

这**不能**推出「格式决定语义」：两个不同的 16 位值给出了不同结果，恰恰说明服务端是按**该设备号自身的签到记录**判定的——`1234567890123456` 很可能是某个流行脚本的默认值，当日已被签过。

**结论**：只能确定 `claim` 需要一个**格式合法**的 `X-Device-Id`（缺省即 9004）。16 位纯数字是「与真实客户端形态一致」的低成本默认值，**按形态对齐采纳，不当作实测更优**。格式收敛在 `DEVICE_ID_LEN` 常量一处，便于将来一次改动切换。

### 2. 设备号派生必须「派生一次即落盘」

否则将来改算法会静默轮换所有账号设备号（全部被服务端视为新设备）。因此派生函数带域前缀 `trae-cc:device-id:v1:`，并把结果持久化，之后只读存储。

## 三、设计

### 3.1 设备标识隔离（新增 `src-tauri/src/api/device_id.rs`）

`Account` 新增 `#[serde(default)] device_id: Option<String>`，与 `machine_id` 彻底解耦（重置签到设备号**不碰** `machine_id`，后者参与 IDE 登录态改写）。

- `derive_device_id(seed) -> String`：SHA-256(域前缀 + seed) 取前 8 字节，映射到 `[1e15, 1e16)` 再 `to_string()`。
  - 用 sha256 而非 `rand(seed)`：rand 的算法/版本演进会改变输出，sha256 恒等。
  - 映射到 16 位整数区间而非 `% 1e16`：后者会产出不足 16 位的值、需补前导零，而任何按数字解析的下游都会丢掉它。
- `resolve_device_id(account) -> String`：`device_id` 优先 → 空则按 `user_id` 派生 → `user_id` 也空则按内部 `id` 派生。
  - 三层回退是为兼容「升级后首次启动、回填尚未落盘」的窗口期。
  - **不能用固定种子兜底**，否则多个无 `user_id` 的账号会撞成同一设备号 → 互相 9095。
- `random_device_id()`：重置用，同一 16 位区间随机。
- 日志一律脱敏（前 4 位…后 2 位）——设备号是准指纹。

回填与重置：
- `AccountManager::new()`（已有 `machine_id` 回填的位置）只回填 `is_none() || is_empty()` 的账号，**绝不无条件重算**。
- 新增 `reset_account_device_id(account_id)`：`random_device_id()` + 清冷却 + 清 `last_checkin_date` + 单次落盘。
  - 清 `last_checkin_date` 的理由：9095 时日期已被写入（Already 语义），不清则重置后自动签到仍跳过，自救无效。
  - 清冷却的理由：让重置后立即可试。注意 **9074 是账号级限流**（AGENTS.md §5.7：同一时刻不同账号结果不同），与设备号无关——重置不保证解除限流，若复现会按策略表重新冷却，代价仅是多打一次请求。
  - **防双签红线**：持久化数据无法区分「今日 9095（未拿积分）」与「今日真签到成功」，清日期后理论上存在同日二次 `claim` 通路。唯一防线是 `checkin_with_token` 中 **claim 前必先查 status**（账号级 `checked_in=true` 短路为 Already）——该顺序禁止改动、禁止绕过。前端「重置设备标识」菜单必须带确认对话框，文案注明「今日已签到成功的账号重置后不会重复获得积分」。
- **不做**「批量重置全部账号」：性质会从「单账号修复」变成「批量规避设备维度限制」，超出本工具边界。

### 3.2 冷却状态机 + 防重入（新增 `src-tauri/src/api/checkin_guard.rs`）

`Account` 新增单个嵌套字段（而非平铺两个，避免「until 有值但 reason 为空」的非法中间态）：

```rust
#[derive(Debug, Clone, Serialize, Deserialize)]
pub struct CheckinCooldown {
    pub until: i64,      // UTC 秒；i64::MAX = 需人工介入
    pub reason: String,  // 机器可读码：auth_expired/rate_limited/risk_control/server_error
}
```

策略表：

| 情况 | 冷却 | 可重试 |
|---|---|---|
| 9074 `rate_limited` | 10 分钟 | 是 |
| HTTP 429 | 60 秒 | 是 |
| HTTP 404 | 60 秒 | 是 |
| 5xx / 网络类 | 2 分钟 | 是 |
| 1005 权益不足 | 12 小时 | 否 |
| 401 / 1001 | `i64::MAX`（需重新登录） | 否 |
| 9095 设备维度已签到 | 不冷却 | —（Already 语义、写 `last_checkin_date`；它是「重置设备号」的触发信号而非错误） |
| 9004 设备号缺失/非法 | 不冷却 | 否（设备号隔离后不应再出现，出现即回归信号：Failed 直报、进失败汇总） |
| `enable=false` 活动未开放 | 不冷却 | 否（追认现状：Failed，不写日期） |

三条硬约束：
- **所有非永久冷却钳制到当日 23:59:59（本地时区），写入时与读取时双重钳制**：`apply_cooldown` 落盘前钳一次，`is_cooling_down` 判定前再钳一次——后者天然覆盖手改 `accounts.json` 与时钟回拨，无需启动校正逻辑。`clamp_to_today_end` 必须先取**本地时区的当日结束时刻**再转 UTC 秒存储：`last_checkin_date` 用 `chrono::Local` 本地日期判定「今日」，按 UTC 日界钳制在中国时区会钳到北京时间 07:59:59，「跨天必重试」直接破洞。项目约定「9074 不写 `last_checkin_date`，下次启动自动重试」，若冷却能跨天就会静默放弃一整天。钳到当日边界后「跨天必重试」成为结构性保证。
- **冷却只作跨批次记忆，准入只读「批次开始前已存在的冷却」**：批次运行期间产生的失败只进内存待重试集合、不落盘冷却，全部轮次结束后统一落盘（语义分层见 §3.3，否则 10 分钟冷却会把 30 秒后的重试直接拦死）。
- `i64::MAX` 哨兵无时钟语义，**禁止参与任何时间换算**；它超出 JS 安全整数范围、JSON 反序列化后等值判断不可靠，前端判定一律按 `cooldown_reason == "auth_expired"` 渲染「需重新登录」，不读数值。`auth_expired` 冷却必须在 Token 成功刷新 / 重新登录 / 编辑账号时清除，且**仅清该 reason**（刷新 Token 不该解除 9074 限流冷却）。

**去掉** 5xx 累计阈值：需额外持久化计数 + 定义重置时机，而自动签到每进程只跑一次，进程内计数意义有限；2 分钟冷却叠加批次重试轮已产生阶梯退避。

防重入用进程级 static（而非 `AppState` 字段）：

```rust
static CHECKIN_GUARD: LazyLock<Mutex<()>> = LazyLock::new(|| Mutex::new(()));
pub fn try_acquire() -> Option<MutexGuard<'static, ()>> { /* try_lock */ }
```

- 为什么不用 `AppState`：`--silent` 在 `lib.rs:1548` 自建 `AccountManager`、不构建 `AppState`，作用域覆盖不到。
- `tokio::sync::Mutex::try_lock` 是对信号量的 CAS，无 TOCTOU，恰好一个调用方获胜；`MutexGuard<'_, ()>` 是 `Send`，可跨 `.await` 持有（`std::sync::Mutex` 会让 future 非 `Send` 直接编译失败）。
- 用标准库 `std::sync::LazyLock`（工具链 1.98.1 已支持），不引入 `once_cell`。
- 必须在**最外层入口**获取并持有到全部结束（含重试的 sleep），否则睡 90s 期间会被第二个批次穿透。注意持锁期间**单账号手动签到同样被拒**（返回「进行中」）——这是简化锁粒度的有意取舍，不拆分。
- 手动入口（单账号/全部）同样遵守冷却准入，**不设跳过通道**；前端对冷却账号展示剩余时间。逻辑最简，且 60 秒级短冷却无绕过价值。
- 已知边界（写进注释）：static 只保护同进程；GUI 与开机自启的 `--silent` 可能并发。**不做跨进程文件锁**——最坏得到 9095/9074，且 9074 有冷却兜底，复杂度与收益不成比例。
- `reset_account_device_id`（§3.1）**同样走 `try_acquire`**：批次签到进行中执行重置，批次末尾的 `apply_checkin_outcomes` 会把重置前收集的旧日期/旧冷却写回、覆盖重置效果。

新增 `CheckinState::Cooldown`（前端区分展示）：冷却账号报 `rate_limited` 会误导、报 `failed` 会触发失败汇总，语义应是「本次未尝试、非错误」。`CheckinResult` 加 `cooldown_until: Option<i64>` 与 `cooldown_reason: Option<String>`——前端按 reason 渲染，不读数值（见上硬约束第三条）。

### 3.3 失败重试（仅 `auto_checkin_pending`）

新增 `CheckinError::Transient`：把「网络超时 / 5xx / 404」与「活动未开放 / 参数错误」拆开，只有前者可重试。`AuthExpired` 不进外层重试（`process_account` 内已有「刷新 Token 后立即重试一次」）。

**必须做成批次级轮次，而非账号级重试**：账号级的最坏耗时随账号数线性增长（5 个限流账号 ≈ 10 分钟）且全程持锁；批次级把等待次数固定为 2 次：

```
第1轮全量 → 收集可重试项 → 睡 30s → 第2轮 → 睡 90s → 第3轮 → 结束
```

最坏 ≈ 2 分钟，与账号数无关。前端 `App.tsx:290` 是 fire-and-forget，2 分钟不影响 UI；代价是持锁期间点「全部签到」会收到「签到进行中」（仅当存在可重试账号时才 sleep，正常全成功零等待）。

**语义分层（关键，防冷却与重试互相架空）**：冷却管「跨批次记忆」，重试轮管「批次内退避」，两者作用域不同。若每轮末尾就落盘冷却、下一轮重新准入，10 分钟的 9074 冷却会把 30 秒后的第 2 轮直接拦死，重试机制名存实亡。因此：
- 批次启动时快照一次已有冷却做准入，**批次运行期间不重新准入**；
- 第 2/3 轮只重试**上一轮返回 `Transient` / `RateLimited`** 的账号（内存集合，不读存储）；
- 批次内失败**不落盘冷却**；全部轮次结束后，最终失败项的冷却与成功项日期统一 `apply_checkin_outcomes` 一次写盘。手动入口单轮结束即落盘。

### 3.4 6 层设备标识重置（新增 `src-tauri/src/device_reset.rs`）

已覆盖：`machineid` 文件、`storage.json` telemetry 三件套、注册表 `MachineGuid`、各类缓存。

**新增 aha 层**——外科式删单键，不删文件：

```rust
pub fn reset_aha_device_id(trae_path: &Path) -> Result<()>
```

- **键是嵌套结构（本机实测，勿按顶层实现）**：`{"tiny_storage_data":{"aha.device.device_id":…, "aha_access_policy":…, "aha_doctor_domain":[], "aha_last_renderer_oom":false}}`。实现必须定位 `tiny_storage_data` 子对象后仅移除其内 `aha.device.device_id`；子对象或键不存在视为已重置（幂等成功）。**切勿在顶层 `remove`**——会静默落空，且 best-effort 风格会把失败吞掉，极难发现。保留同层 `aha_access_policy`（服务端下发的策略 blob，删了只会多一次往返且无隔离收益）/ `aha_doctor_domain` / `aha_last_renderer_oom`，也避免未来新增键被我们的重写抹掉。
- 写回必须**原子化**（写同目录临时文件 + rename）：进程崩溃时直写会把「外科式删除」变成「文件截断」。`accounts.json` 的批次写盘沿用现有 `save_store` 直写（既有行为，本次不改）。
- **不能写"合法值"**：该值是加密 blob，密钥不在我们掌握中，写入非法值会让客户端解密路径异常——删除永远比伪造安全。
- 解析失败时保持原样（把「重置」变成「数据丢失」不可接受），全程 best-effort 不中断切换流程。
- 风险低：登录态在 `storage.json` 的 `iCube*` 键与 `state.vscdb`，与 aha 无关，**不需要重新登录**。唯一真实风险是「Trae 运行中被回写覆盖」，靠调用时序（先 kill）规避。

**确认不该动的两项**（已实测内容）：
- `aha\Remote_State`：纯 feature flag 的 `{name:{params,state}}`，无设备标识 → 不动
- `ahanet\prefs\local_prefs.json`：纯 Chromium `http_server_properties`（QUIC/SPDY、证书链）→ 不动

**待验证后决定**：`Partitions\trae-webview\` 下有独立于默认 profile 的 `Network\Cookies` / `Local Storage\leveldb` / `IndexedDB`，而 `open_pricing` 正是「清 Cookie → 写账号 Cookie → 跳转」的注入点。**先对比切换前后该 Cookie 的 mtime/大小确认有写入，再决定是否纳入**，无证据不盲删。

**顺带修一个既有缺陷**：`clear_trae_login_state`（`machine.rs:734`）不像 `switch_trae_account` 那样先 `kill_trae()`，加入 aha 层后这个不一致会变成实际故障（重置被进程回写覆盖）。处理方式：**若 Trae 正在运行则跳过 aha 重置并告警**（不新增 kill 行为，避免改变既有语义）。

> 注：`machine.rs` 与 `clear_trae_login_state` 有约 155 行重复的清理逻辑。本次**不做**该重构（超出「优化签到系统」范围且风险高），仅在 AGENTS.md 记为待办。

## 五、分阶段实施（每阶段独立可验证）

| 阶段 | 内容 | 验证方式 |
|---|---|---|
| **0** 设备号落地 | `device_id.rs` + 字段 + 回填 + `resolve_device_id` | 启动后 `accounts.json` 每账号多出 16 位 `device_id`；重启值不变；签到仍正常；日志设备号已脱敏。**此阶段不声称 16 位更优** |

## 六、已知限制（写进 AGENTS.md，本次不修）

1. **GUI 与 `--silent` 双进程写 `accounts.json`**：GUI 内存里的 store 会在下次 `save_store()` 覆盖 silent 进程刚写的 `last_checkin_date`/冷却。本次用「批次单次写盘」缩小窗口，但不做读-改-写合并。
2. **子串匹配分类易误判**：`is_auth_error` 用 `contains("401")`、`is_rate_limited` 用 `contains("9074")`，消息里含这些数字就误判——引入冷却后误判代价变成「白等 10 分钟」。故本方案改为**优先用 JSON 数值 `code` 判定**，子串仅作解析失败兜底。
3. **自动签到被 busy 跳过时 `autoCheckinRanRef` 已置位**（`App.tsx:289`），该会话不再重试；可接受。
4. `machine.rs` 与 `clear_trae_login_state` 约 155 行重复清理逻辑待重构。
5. **`--silent` 进程寿命变长**：批次重试轮 + 单请求 20s 超时使无头进程从秒级延长到最坏约 2 分钟（仅当存在可重试账号时发生）。开机自启场景可接受，属有意行为变化。
6. **导出/导入原样携带 `device_id`**：账号导入第二台机器后两边同号，同日签到必有一边 9095。这是「同账号同设备身份」的有意语义，不是 bug，勿按缺陷修复。`checkin_cooldown` 同样随导出携带，冷却时间戳全局一致，跨机保留无害。
7. **每账号独立设备号使 9095 从常态拦截变为近乎绝迹（有意的行为变化，非副作用）**：设备号按 `user_id` 派生后，「一台电脑一天只能签一个账号」的设备维度限制在本工具内被结构性改变。它与 §3.1「不做批量重置」边界声明并存的前提是：设备号静态不旋转、重置仅限单账号自救。连带风险：同一 IP 下多设备号每日签到可能促使服务端把风控升级到账号/IP 维度，届时 9074 冷却策略需要重估。
