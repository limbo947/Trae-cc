# 设备身份隔离调研：能否让 Trae 认为是「新设备登录」

> 起因：用户提出「在应用内登录账号时，让 Trae 认为是新设备登录的，有没有办法」。
> 本轮**只调研不实现**。取证日期 2026-09-20，取证对象为本机 Trae CN + trae-cc 现有实现。
> 结论先行：**「登录」这个动作本身没有任何可改的设备标识字段**；能控制的只有 Trae 客户端的本地标识，而现状已覆盖大部分。曾把 `Partitions` 初判为「缺口」，**提取键名后实测否定**——那是内置浏览器的用户数据，与设备身份无关，**不应处理**（见 §3）。剩余可做的只是让缓存与派生标识更干净，无法突破服务端维度的判定。

---

## 1. 先厘清：这里有四个不同的「设备」

把它们混为一谈，是这个问题看起来"有办法"的主要原因。

| 层面 | 内容 | 谁能控制 |
|---|---|---|
| A. 登录请求 | trae-cc 调 Trae 的登录 API 时，服务端能看到什么 | 可选字段极少（见 §2.1） |
| B. 浏览器环境 | trae-cc 内置 webview（WebView2）打开登录页时的浏览器指纹 | 可隔离（见 §2.2） |
| C. 客户端本地标识 | Trae CN.exe 上报设备身份时读的本地文件/注册表 | **主要着力点**（见 §2.3） |
| D. 服务端判定 | Trae 服务端如何认定「这是不是新设备」 | **不可控**（见 §2.4） |

---

## 2. 逐层取证

### 2.1 登录 API 链路：没有任何设备标识字段

实测 `login_with_email`（`src-tauri/src/api/trae_api.rs:805-920`）的完整链路：

1. `GET https://www.trae.com.cn/login` —— 只为拿初始 Cookie
2. `POST https://api.trae.com.cn/passport/web/email/login/`（`aid=677332`、`account_sdk_source=web`、`sdk_version=2.1.10-tiktok`），body 为 XOR(0x05) 编码的 email/password
3. `POST https://api.trae.com.cn/cloudide/api/v3/trae/Login?type=email`
4. `POST {api_base}/cloudide/api/v3/common/GetUserToken` —— 换取 JWT

**全部请求头只有**：`User-Agent`（硬编码浏览器 UA）、`Origin`、`Referer`、`Content-Type`、`Cookie`。
**没有** `X-Device-Id`、`X-Machine-Id`、`X-Device-Name` 或任何等价字段。

对照：只有**签到**接口用 `X-Device-Id`（`checkin.rs:217-233`），且用的是 trae-cc 自己派生的 16 位签到设备号（`Account.device_id`），与 IDE 机器码**刻意解耦**（见 `doc/签到系统优化方案.md` §3.1）。这与"登录"是两条独立链路。

> 结论：想通过"登录请求"告诉服务端「我是新设备」，**没有可改的字段**。改 UA 之类的动作不构成设备身份，反而更像异常客户端。

### 2.2 浏览器登录用的 webview：两个窗口共用同一份数据目录

- 登录窗口 `trae-login`（`lib.rs:849`）与购买窗口 `trae-pricing`（`lib.rs:1499`）都用 `WebviewWindowBuilder::new` 创建，**均未指定 `data_directory`**。
- 实测 trae-cc 的 webview 数据落在：`%LOCALAPPDATA%\com.hhj.trae-cc\EBWebView`。
- 由于未指定独立目录，**两个窗口共享同一份 Cookie / Local Storage / IndexedDB**。即：登录 A 账号后，购买窗口会带着 A 的会话；登录 B 账号后，购买窗口会带着 B 的会话。

这一层可以隔离（`data_directory` 或登录前清理该目录），但它隔离的是**浏览器环境**，与 Trae CN.exe 的设备身份无关。服务端是否用浏览器指纹做设备判定，本地无法验证。

### 2.3 Trae 客户端的本地标识（真正的着力点）

现状覆盖度（代码依据：`machine.rs` 的 `switch_trae_account` 步骤 ⓪a–⑫）：

| 层 | 位置 | 现状处理 | 可控性 |
|---|---|---|---|
| `machineid` 文件 | `%APPDATA%\Trae CN\machineid` | 写入**账号绑定**的 UUID（每账号独立） | ✅ 完全可控 |
| telemetry 三件套 | `storage.json` 的 `telemetry.machineId` / `devDeviceId` / `sqmId` | 写入新值（machineId 由 machineid 派生） | ⚠️ 客户端可能覆盖，见 §4.2 |
| aha 设备标识 | `aha\TinyStorage` 的 `aha.device.device_id` | **删除**，让客户端重新生成 | ⚠️ 只能删、不能指定值 |
| 注册表 `MachineGuid` | `HKLM\SOFTWARE\Microsoft\Cryptography` | 写入账号绑定值 | ⚠️ 需管理员，非管理员静默失败 |
| Chromium 会话层 | `state.vscdb` / `Local State` / `IndexedDB` / `Local Storage` / `Session Storage` / `Cookies` | 删除 | ✅ |
| `Partitions\*` | 见 §3 | **未处理** | ❓ 待确证 |

**为什么 aha 只能删不能写**：该值是加密 blob，密钥不在我们掌握中；写入非法值会让客户端解密路径异常（`device_reset.rs:50-51` 有明确注释）。删除后由客户端按自己的规则重新生成——这反而是"新设备"的正确姿势。

### 2.4 服务端维度：本地怎么改都盖不住

- **登录 IP**：同一网络下多账号必然同 IP，这是最强的关联信号。
- **账号的历史设备列表**：服务端侧数据，本地改不了。若服务端记录"该账号曾在设备 X 登录"，换本地标识也不会抹掉这段历史。
- **TLS / HTTP 指纹**：trae-cc 用 `reqwest` 发请求，其 TLS 栈（JA3/JA4 类特征）与真实浏览器、与 Trae 的 Electron 客户端都不同——**这本身就是一个"非官方客户端"的强指纹**。这一步无法通过改本地文件消除。

> 因此「让 Trae 认为是新设备」在服务端侧是**无法保证**的：本地标识全部换新，仍可能被 IP + TLS 指纹 + 行为模式关联。

## 3. `Partitions`：实测否定 —— 与 Trae 设备身份无关，不应处理

### 3.1 实测：它们在写入，但写的是「浏览器数据」

`%APPDATA%\Trae CN\Partitions\` 下两个 profile：

| profile | 会话类目录（体积 / 最近写入） | 可再生缓存 |
|---|---|---|
| `trae-webview` | Local Storage 7.1 MB（09-20 03:14）、IndexedDB 37 KB、Network 82 KB、Session Storage 30 KB | Cache **344 MB**、Code Cache 78 MB |
| `icube-web-crawler-shared-session-v1.0` | IndexedDB 257 KB、Local Storage 175 KB（09-19 01:35）、Network 120 KB、Session Storage 105 KB | Cache 85 MB、Service Worker 45 MB |

写入时间与 Trae 运行时间吻合 → 确实在写，不是死目录。

### 3.2 证据反转：里面没有一个 Trae 的东西

第一轮只做 ASCII 子串检索时曾命中 `device` / `uid` / `token`，看着很像设备标识。**提取具体键名后结论完全反转**——把两个 profile 的「来源 origin + 键名」全量提取：

`trae-webview\Local Storage`（53 个键，节选）：

```
http://127.0.0.1:3080         ==>  dsh.conversation.session-…、dsh.sessions.current、dsh.workspace.view.v5
http://localhost:8081         ==>  bizyair_cached_user_info、llm_custom_presets、@total_coins_spent
http://localhost:4321         ==>  site-theme-overrides、site-cfg-overrides
https://github.com            ==>  jump_to:page_views、ref-selector:Donchitos/…、offline_cache_…
https://www.figma.com         ==>  STATSIG_LOCAL_STORAGE_STABLE_ID
https://marketing.figma.com   ==>  _gcl_ls
https://signin.volcengine.com ==>  version.…BytePlus_Console.zh
https://www.baidu.com         ==>  safeIconHis、wwwPassLogout
```

`icube-web-crawler-shared-session-v1.0\Local Storage`（21 个键，节选）：

```
https://www.bilibili.com ==>  bilibili_player_gpu_renderer、1.b
https://www.toutiao.com  ==>  tt_scid
https://www.qidian.com   ==>  w_tsfp
https://fanqienovel.com  ==>  web_security_runtime_cache
（其余为 baike / ibiling / 腾讯科幻书城等浏览站点）
```

**零个键来自 `trae.com.cn`。** 再查 `trae-webview\Network\Cookies` 的域名分布：

```
figma x38、volcengine x34、baidu x20、github x4、127.0.0.1 x2
trae.com.cn / trae.cn → 0 命中
```

### 3.3 结论：内置浏览器的用户数据，不是设备标识

- 这两个 profile 是 Trae 客户端**内置浏览器**（AI 面板打开的网页、联网检索的共享会话）的通用 Chromium profile，装的是**用户自己访问过的站点**的 Cookie 与 Local Storage。
- 先前那批 `device` / `uid` / `token` 命中是**子串误命中**（站点自身脚本里的字段名），具体键名清单里没有任何 Trae 相关项。
- 因此「TraeCode 未处理 `Partitions` 是口径不一致的缺口」这一初判是**错的**，此处更正。

→ **TraeCode 不应处理 `Partitions`**：切换是删除式语义，删掉会真的丢掉用户在内置浏览器里的登录态与浏览记录（figma / github / 本地开发服务等），而对设备身份**零收益**。
→ 与 TraeWork 的「不一致」也无需消除：TraeWork 是**快照/恢复**（拷走再还原，纳入会话子路径是为了完整还原账号上下文），TraeCode 是**删除**（纳入只剩损失）。场景不同，口径本就该不同。
→ 唯一与设备标识沾边的是 `Partitions\trae-webview\Trust Tokens`（36 KB）——那是 Chromium 的 Trust Token 功能文件，文件名含 `token` 造成的误命中，同样与 Trae 无关。

## 4. 另外两处待确证项

### 4.1 `telemetry.machineId` 的派生关系对不上（2026-09-20 实测）

- 代码里 `generate_telemetry_machine_id`（`machine.rs:849`）用 **sha256(machineid)** 生成该值。
- 本机实测：`sha256(当前 machineid)` = `97da5d26…`、`sha256(旧 machineid)` = `788ed629…`，**都与实际 `telemetry.machineId`（`222e677a…`）不符**。
- 推测该值由客户端自行维护；trae-cc 写入的规则可能不被认可或在下次启动被覆盖。**若为真，则"写入 telemetry"这一步对设备身份没有实际贡献**——需要设计一次切换后立即对照的实验来定论（会真实改动登录态，需授权）。

### 4.2 aha 层的"重新生成"是否每次都会产生新值

现状是删除 → 客户端生成。但**未验证**客户端是否在首次启动时立刻生成、以及是否可能复用其他来源的值。同样需要一次带观察的切换实验。

## 5. 若要动手，建议的优先级

按「性价比 + 风险」排序，且**每一步都要先取证**：

1. ~~补齐 `Partitions` 会话子路径~~ —— **已排除**：§3.3 实测证明它与 Trae 设备身份无关（全是用户浏览数据），删除只会丢用户数据、对设备身份零收益。**TraeCode 维持现状即可。**
2. **登录 webview 的环境隔离**：给 `trae-login`（必要时含 `trae-pricing`）指定独立 `data_directory`，或登录前清理 `EBWebView`。收益是"每次登录像全新浏览器"，但**与 C 层设备身份无关**，不要高估。
3. **把"写入"改为"删除 + 让客户端生成"**：对 telemetry 三件套，在 4.1 确证为"客户端维护"后，删除可能比写死更干净。
4. **管理员权限提示**：注册表那一步非管理员时静默失败，导致两层标识不一致——至少应在界面上提示。

## 6. 边界与风险（必须明确）

### 项目已确立的边界（既有决策，本次调研不推翻）

- `doc/TraeWork账号切换计划.md:291`：**不批量重置设备标识、不做账号倒卖用途**。
- `doc/签到系统优化方案.md:55`：**不做「批量重置全部账号」**——性质会从「单账号修复」变成「批量规避设备维度限制」，超出本工具边界。

### 风险判断

- **设备身份频繁轮换本身就是风控强特征**：正常用户的机器不会每次登录都变成新设备。做得越"彻底"，越可能触发更严格的风控（异常登录、二次验证、封禁），与用户想要的"正常使用"目标相反。
- **"新设备登录"若被用于绕过限制**（如免费额度上限、设备维度的每日额度），则与上一条边界直接冲突。

### 建议的定位

本工具现有的行为——**切换账号时保证两个账号的设备标识互不相同**（每账号独立 machineid + 删除 aha + 清缓存）——是"账号隔离"性质，属于多账号工具的合理范围，且**已经实现**。

而"每次登录都换一套新设备身份"属于"身份轮换"，两者界限在于**是否以规避服务端限制为目的**。建议：**不实现后者**，仅把 §3 的残留清理补齐（它的正当理由是"换账号就该把上一个账号的痕迹清干净"）。

## 8. 明确不做

- 不实现"每次登录换新设备身份"（§6 边界与风险）。
- 不做批量设备标识重置。
- 不尝试伪造 aha 加密 blob（密钥不在手，写入非法值会造成客户端解密异常）。
- 不改 `ModularData` 等业务数据（跨账号替换会串数据）。
- 不动 `aha\Remote_State`（纯 feature flag）与 `ahanet\prefs\local_prefs.json`（纯 Chromium http_server_properties）——已实测无设备标识。
