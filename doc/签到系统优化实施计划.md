## 阶段 0：设备号落地

**目标**：`Account` 增加与 `machine_id` 完全解耦的 `device_id`，签到请求改用它；派生一次即落盘，之后只读存储。

### 任务

1. 新建 `src-tauri/src/api/device_id.rs`（约 60 有效行）：
   - `pub const DEVICE_ID_LEN: usize = 16` —— 格式收敛点，将来改形态只动这一处。
   - `derive_device_id(seed: &str) -> String`：SHA-256(`trae-cc:device-id:v1:` + seed) 取前 8 字节为 u64，映射到 `[1e15, 1e16)` 后 `to_string()`。用 sha256 而非 `rand(seed)`：rand 算法/版本演进会改输出，sha256 恒等。映射到区间而非 `% 1e16`：后者产出不足 16 位需补前导零，按数字解析的下游会丢掉。
   - `resolve_device_id(account: &Account) -> String`：`device_id` 非空优先 → 按 `user_id` 派生 → 按内部 `id` 派生。三层回退只为兼容「升级后首次启动、回填尚未落盘」窗口期；**禁止固定种子兜底**（多个无 `user_id` 账号会撞号互踢 9095）。
   - `random_device_id() -> String`：重置用，同一 16 位区间随机（复用 `rand` 依赖）。
   - `mask_device_id(id: &str) -> String`：前 4 位…后 2 位，供日志使用。
2. `src-tauri/src/api/mod.rs`：`pub mod device_id;`。
3. `src-tauri/src/account/types.rs`：`Account` 加 `#[serde(default)] pub device_id: Option<String>`；`Account::new` 用 `derive_device_id(&user_id)` 派生（`user_id` 为空则落 `None`，交给回填/解析回退）。
4. `src-tauri/src/account/account_manager.rs`：`AccountManager::new()` 在现有 `machine_id` 回填旁加 `device_id` 回填，条件 `is_none() || is_empty()`，**绝不无条件重算**；回填后随既有 `changed` 标志单次落盘。
5. `src-tauri/src/api/checkin.rs`：`process_account` 中 `let device_id = account.machine_id…`（L305）改为 `resolve_device_id(account)`；日志打印设备号处改 `mask_device_id`；同步更新模块头部与 `build_headers` 处「用账号机器码」的过时注释。
6. `src/types/index.ts`：`Account` 加 `device_id?: string | null`。

### 验收

- 启动后 `accounts.json` 每账号多出 16 位纯数字 `device_id`；重启值不变。
- 手动签到一次成功（行为与改动前一致）；日志中设备号已脱敏。
- `cargo check` + `npx tsc --noEmit` 通过。
- 此阶段**不声称 16 位更优**，仅形态对齐真实客户端。

### 回滚

还原 `checkin.rs` 一行取值即可；`device_id` 字段留盘无害（`#[serde(default)]` 兼容）。

## 阶段 1：防重入 + 冷却状态机

**目标**：三入口互斥；限流/服务器错误进入有界冷却；分类改为数值 code 优先。

### 任务

1. 新建 `src-tauri/src/api/checkin_guard.rs`（约 110 有效行）：
   - `static CHECKIN_GUARD: LazyLock<Mutex<()>>`（`std::sync::LazyLock` + `tokio::sync::Mutex`）+ `try_acquire() -> Option<MutexGuard<'static, ()>>`。选址理由：`--silent`（lib.rs:1548）自建 `AccountManager` 不经 `AppState`，static 才覆盖得到；`try_lock` 是 CAS 无 TOCTOU；`MutexGuard<()>` 是 `Send` 可跨 `.await` 持有。
   - 冷却策略表（集中一处函数，勿散落）：9074→10min；HTTP 429/404→60s；5xx/网络类→2min；1005→12h（不可重试）；401/1001→`i64::MAX`（reason=`auth_expired`）。9095/9004/`enable=false` **不冷却**（见方案 §3.2 策略表补格）。
   - `clamp_to_today_end(until: i64) -> i64`：先取**本地时区**当日 23:59:59 再转 UTC 秒（`last_checkin_date` 是本地日期，UTC 日界会把跨天保证钳穿）；`i64::MAX` 哨兵原样透传。钳制在**写入与读取两侧**都执行：`apply_cooldown` 落盘前钳一次，`is_cooling_down` 判定前再钳一次——读取侧钳制覆盖手改数据与时钟回拨，免启动校正逻辑。
   - `is_cooling_down(account) -> Option<i64>` / `apply_cooldown(...)` / `clear_auth_cooldown(...)`（仅清 `reason == "auth_expired"`，刷新 Token 不该解除限流冷却）。
2. `src-tauri/src/account/types.rs`：新增 `CheckinCooldown { until: i64, reason: String }`（嵌套单字段，杜绝「until 有值 reason 空」的非法中间态）；`Account` 加 `#[serde(default)] pub checkin_cooldown: Option<CheckinCooldown>`。
3. `account_manager.rs`：`mark_checkin_done` 升级为 `apply_checkin_outcomes(&[(account_id, date/冷却变更)])`，**批次单次写盘**；`save_refreshed_token` 内联清 `auth_expired` 冷却。
4. `checkin.rs`：
   - 三入口（`checkin_one_account` / `checkin_all` / `auto_checkin_pending`）最外层 `try_acquire`，失败返回「签到进行中」；guard 持有到全部结束（含阶段 2 的 sleep）。
   - 准入：**批次启动时快照一次已有冷却**，冷却中账号直接产出 `CheckinState::Cooldown`（不请求）；批次运行期间不重新准入（为阶段 2 重试轮让路）。`CheckinResult` 加 `cooldown_until: Option<i64>` 与 `cooldown_reason: Option<String>`——`i64::MAX` 超出 JS 安全整数、等值判断不可靠，前端一律按 reason 判定。
   - 分类改造：`classify_error(code: Option<i64>, http_status: Option<u16>, text: &str)` 改为**优先用 JSON 数值 `code`**（9074/9095/1001/1005/9004），HTTP 状态码供 429/5xx 归类，两者由 status/claim 解析点与 `post_with_fallback` 透传；子串匹配仅作解析失败兜底——引入冷却后误判代价是「白等 10 分钟」。
   - 新增 `CheckinError::Transient`（网络超时/5xx/404）与永久错误分离，供阶段 2 重试判定；`AuthExpired` 不进外层重试（`process_account` 内已有刷新重试一次）。
   - `run_for_accounts` 末尾统一 `apply_checkin_outcomes` 一次落盘（成功/Already 写日期 + 各类冷却），替代每账号一次 `save_store`；**自动签到多轮次场景改为全部轮次结束后统一落盘一次**（见阶段 2 任务 2）。
5. `src/types/index.ts`：`CheckinCooldown` 类型；`Account.checkin_cooldown?`；`CheckinState` 联合加 `"cooldown"`；`CheckinResult.cooldown_until?: number | null` 与 `cooldown_reason?: string | null`。
6. `src/App.tsx`：签到结果处理加 `cooldown` 分支——info 提示「冷却中，剩余 N 分钟」、不刷新用量、批量汇总单列「冷却」一项；按 `cooldown_reason === "auth_expired"` 渲染「需重新登录」（不读数值）；「签到进行中」按 info 展示而非 error toast；**cooldown 提示仅作用于手动入口，自动签到维持既有静默语义**（App.tsx:304 只记 console）。

### 验收

- 连点两次「全部签到」→ 第二次返回「进行中」；批次进行中单账号手动签到同样被拒（有意取舍）。
- 9074 账号出现 10 分钟冷却，重启应用后仍在（落盘生效）。
- 手改 `accounts.json` 把某账号 `until` 改成明日时间戳 → 读取判定时被钳回当日 23:59:59（本地时区，读取侧钳制生效）。
- 触发一次 Token 刷新 → 仅 `auth_expired` 冷却被清，限流冷却保留。
- 汇总 toast 中冷却账号单列，不计入失败。

### 回滚

字段均 `#[serde(default)]`，还原代码后旧版本可读新数据；冷却字段残留无害。

## 阶段 2：批次重试轮次（仅 `auto_checkin_pending`）

**目标**：可重试失败（`Transient` / 9074）按批次轮次重试，等待次数与账号数解耦。

### 任务

1. `auto_checkin_pending` 改为轮次驱动：第 1 轮全量 → 收集 `Transient`/`RateLimited` 账号 → 睡 30s → 第 2 轮 → 睡 90s → 第 3 轮 → 结束。日志打印「第 N 轮…可重试 M 个…等待 Ns」。
2. **语义分层（防冷却与重试互相架空的硬规则）**：待重试集合是**内存态**（上一轮返回 `Transient`/`RateLimited` 的账号），第 2/3 轮不重新走冷却准入；批次内失败**不落盘冷却**，全部轮次结束后才把最终失败项的冷却与成功项日期统一 `apply_checkin_outcomes` 一次写盘。若每轮落盘冷却再准入，10 分钟冷却会把 30 秒后的重试直接拦死，重试机制名存实亡。
3. 仅当存在可重试账号才 sleep（正常全成功零等待）。
4. 手动入口（`checkin_one_account` / `checkin_all`）**不重试**，保持现状（单轮结束即落盘冷却）。

### 验收

- 构造 2 个限流账号自动签到：日志见两轮 sleep，总耗时 ≈2 分钟且与账号数无关；且第 2/3 轮**真实发起了重试请求**（未被首轮失败拦截——回归验证语义分层）。
- 无重试项时自动签到零额外等待。
- 持锁期间点「全部签到」返回「进行中」；前端 fire-and-forget（App.tsx:290）不受影响。

### 回滚

还原 `auto_checkin_pending` 为单轮调用即可，无持久化变更。

## 阶段 3：重置设备号能力 + 前端

**目标**：单账号设备号可旋转，用于 9095 自救；防双签红线落地。

### 任务

1. `lib.rs`：`#[tauri::command] async fn reset_account_device_id(account_id, state)` → **先 `try_acquire()` 防重入**（批次签到进行中执行重置，批次末尾的 `apply_checkin_outcomes` 会用重置前收集的旧日期/旧冷却覆盖重置效果；持锁失败返回「签到进行中」）→ 调 `device_id::random_device_id()` + manager 落盘入口（清冷却 + 清 `last_checkin_date`，单次写盘）；注册进 `generate_handler!`。
2. `api.ts`：`export async function resetAccountDeviceId(accountId: string)` —— 本地命令用 `invoke`（非 `invokeNetwork`）。
3. `src/components/ContextMenu.tsx`：右键菜单加「重置设备标识」，**先弹确认对话框**，文案须注明「今日已签到成功的账号重置后不会重复获得积分」（防双签红线的用户侧表达）。
4. 重置成功后 toast 提示「设备标识已重置，下次自动签到将重试该账号」。

### 验收

- 重置后 `accounts.json` 中该账号 `device_id` 为新 16 位随机值、冷却与 `last_checkin_date` 均清空。
- 下次自动签到重试该账号；若该账号今日已真签到成功，重试被 status 前置查询短路为 Already（红线生效，无二次 claim）。
- `machine_id` 全程不变（与 IDE 登录态解耦）。

### 回滚

删除命令注册与菜单项；已重置的设备号可继续使用，无数据风险。
